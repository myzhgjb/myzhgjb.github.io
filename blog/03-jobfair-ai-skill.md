上周整理苏大那场招聘会，从查活动、拿表、分类、筛岗到做投递清单，前后花了三个多小时。

下次还有别的招聘会。我不想再花三个小时。

所以把整个流程固化成了一个 AI Skill——**丢给它一句话，它自己跑完六步，产出三件套。**

## 三件套是什么

| 产物 | 什么时候用 | 形态 |
|---|---|---|
| 全量分类库 | 到场前通读、现场查企业 | 单个 HTML，断网可用 |
| 背景匹配表 | 决定主攻哪几家 | 按技术栈打分排序 |
| 手机投递清单 | 现场打勾、事后导出 | PWA，装到桌面像 App |

**为什么不是一个页面？** 因为这三件事的使用场景完全不同：查资料要全、做决策要少、现场记录要快。塞在一个页面里，哪个都不好用。

## 六阶段

![流程](https://github.com/myzhgjb/jobfair-job-screening/raw/main/docs/pipeline.svg)

1. **活动识别**：确认这场会到底是什么
2. **数据获取**：Excel / 平台接口 / 公众号名单
3. **解析分类**：结构化 + 20 类归类
4. **背景匹配**：读简历，打分排序
5. **投递清单**：生成 PWA 并发布
6. **路线归档**：展位动线 + 目录整理

## 阶段 0 是踩坑踩出来的

第一版我只做了「拿到 Excel 之后」的部分。结果第一次用就翻车了：

我搜「苏州大学 11 月 11 日 招聘会」，命中学校就业网的一场——**金螳螂建筑学院、艺术学院联合双选会，21 家企业**。我就按这个做了整套东西。

但实际那天的活动是**「校园苏州日」全国秋招苏州高校专场，308 家企业**，在体育馆，市级主办。

两个活动同一天、同一所学校、完全不同。

为什么搜错？因为**市级活动不走学校就业网的招聘会系统**，它走市人才办公众号 + 独立的招聘平台，91job 上根本查不到。

于是我把这条写成了阶段 0 的强制流程：

```
1. 查 ≥2 个来源（校就业网 / 校公众号 / 市人才办 / 本地宝）
2. 用参会企业数量级反推（公众号说 300+，91job 只有 21 家 → 不是同一场）
3. 用场地反推（体育馆 vs 某楼层招聘大厅）
4. 确认主办单位（学院主办 = 专业限定；市人才办 = 全行业）
5. 有多个候选就全部列出让用户选，不要替用户拍板
```

**教训：让 AI 做事，最贵的错误不是做错，是「基于错误的前提做对了一切」。**

## 把 HTML 做成模板，只注入数据

三件套不重新写页面，全部是「模板 + 数据注入」：

```python
tpl = open('library_template.html').read()
html = tpl.replace('__DATA__', json.dumps(data, ensure_ascii=False))
```

模板里保留一个 `<script id="DATA" type="application/json">__DATA__</script>`，
页面逻辑完全由数据驱动（类别、优先级、技术要点全在 JSON 里）。

这样换一场招聘会，只需要跑一次解析脚本，页面一行不用改。

同样思路用在 PWA 上：`assets/pwa/` 整个目录复制过去，注入数据，改一下 `localStorage` 的 KEY 就完事。

```js
const KEY = 'szd1111.apply.v1';   // 每场招聘会换一个，避免数据串台
```

## 投递清单为什么要 PWA 而不是普通网页

现场的真实场景：一只手拿简历，一只手拿手机，网络很差。

普通网页刷新一下就丢状态。PWA 三个好处：

1. **localStorage** 存勾选，切后台、锁屏、刷新都不丢
2. **加到主屏幕**后有独立图标、全屏、无地址栏，跟原生 App 一样
3. **Service Worker** 缓存后断网也能开——体育馆里信号通常很差

导出功能是给自己留后路：投完点「导出 Markdown」，复制成文字直接丢给 AI，让它整理进投递总表。

> 注意：这是 PWA，不是 APK。真 APK 要 Android SDK 打包，成本高得多，收益几乎没有。

## 一条不能破的底线

招聘会 Excel 通常只有 5–6 列。**没有企业规模，也没有 JD 正文。**

AI 最容易犯的错不是不会做，是**用看起来合理的内容填补空白**。

所以 Skill 里写死了一条：

> 原始表没有的字段，不许编造。

具体落地：

- 企业规模只有能从简介正则读到「员工 XXX 人」时才写，其余标**「规模未披露」**
- 岗位技术要求由类别模板生成，页面顶部明写**「推断，不是官方 JD」**
- 行业按名称推断，注明**「不是官方展区划分」**

我在页面上用了一个黄色提示框专门说这件事。**丑一点没关系，误导人不行。**

## 质量检查清单

Skill 里带了一张清单，每次交付前过一遍：

- [ ] 活动信息有 ≥2 个来源，企业数量级能对上
- [ ] 页面明确写了「哪些字段原始表没有」
- [ ] 全量库企业数 / 岗位数与 Excel 行数对得上
- [ ] 手机 390px 无横向溢出（`scrollWidth === clientWidth`）
- [ ] 投递清单勾选刷新后仍在
- [ ] 所有 HTML 不依赖外网 CDN，断网可打开
- [ ] 交付目录里没有临时文件和截图

**清单比文档有用。** 文档写「要注意移动端适配」，清单写「390px 无横向溢出」，后者才会被执行。

## 现在的用法

装好之后，直接说人话：

```
帮我准备 11 月 11 日苏州大学的招聘会
```

它会自己判断这场是什么活动、去拿表、出三件套。有 Excel 就直接丢：

```
这是岗位表，按我的背景筛一下，再做个手机上能打勾的投递清单
```

仓库：<https://github.com/myzhgjb/jobfair-job-screening>

## 最后

写 Skill 的过程，其实是**把自己踩过的坑变成别人的默认值**。

第一次做，你要花三小时，还要犯「搜错活动」「21.5% 没分类」「手机端溢出」这些错。
把它写成 Skill，第二次就是一句话。

这也算是 AI 时代比较划算的一种「偷懒」。
